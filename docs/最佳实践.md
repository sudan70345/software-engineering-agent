# 最佳实践

本文档总结在实际使用中验证有效的最佳实践，帮助你更高效、高质量地使用本工程。

## 1. 会话管理最佳实践

### 1.1 在关键门禁点保存状态快照

**为什么**：长会话可能遇到上下文压缩，关键门禁点的快照可以快速恢复进度。

**何时保存**：
```bash
# 阶段 1 完成后（业务基线确认）
./scripts/session-state.sh save

# 阶段 2 完成后（全部页面确认）
./scripts/session-state.sh save

# 需求包定稿后
./scripts/session-state.sh save

# 技术规格完成后（architect-agent）
./scripts/session-state.sh save
```

### 1.2 会话恢复时先自检

**推荐流程**：
```bash
# 1. 运行自检脚本
./scripts/context-recovery-check.sh

# 2. 如果自检通过，直接继续
"继续 {任务名} 的工作"

# 3. 如果自检失败，按提示恢复
"我要继续工作 {工程名} 下的 {任务名} 任务，当前进度是 [阶段描述]"
```

### 1.3 长时间中断后的恢复策略

**场景**：超过 4 小时未操作，或切换到其他工程后回来。

**推荐做法**：
1. 运行 `context-recovery-check.sh` 查看状态
2. 明确告诉 agent：
   - 工程名
   - 任务名
   - 上次停留的阶段（如「阶段 2 已完成 3 个页面」）
3. Agent 会自动读取上下文并复述关键约束

## 2. 需求沟通最佳实践

### 2.1 阶段 1：先确定业务场景，再谈页面

**❌ 不好的做法**：
```
"我要做一个登录页、列表页、详情页"
```

**✅ 好的做法**：
```
"我要做一个任务管理系统，主要有三个业务场景：
1. 新用户首次使用（场景[S1]）
2. 日常任务记录（场景[S2]）
3. 团队协作审批（场景[S3]）
每个场景涉及哪些页面，我们再细化"
```

**为什么**：场景[Sx] 是业务情境的一级容器，先确定场景才能确保页面设计不遗漏、不冗余。

### 2.2 阶段 2：功能优先，UI 其次

**❌ 不好的做法**：
```
"这个页面用卡片布局，顶部有导航栏，底部有 Tab"
```

**✅ 好的做法**：
```
"这个页面要完成以下功能：
- FR-1: 查看任务列表
- FR-2: 筛选任务（按状态/负责人）
- FR-3: 快速创建任务
布局上用卡片展示，顶部筛选栏，右下角悬浮按钮创建"
```

**为什么**：功能点（FR-x）是追溯的脊柱键，先定义功能再谈 UI，确保功能完整且可追溯。

### 2.3 复杂弹窗的判定标准

**辅助页面[N-A]**（独立页面）：
- ✅ 有独立表单 + 校验 + 提交
- ✅ 有自己的业务处理逻辑
- 示例：创建订单弹窗、编辑用户信息弹窗

**简单弹窗**（内联主页面）：
- ❌ 仅操作提醒、确认、结果反馈
- ❌ 无表单、无校验、无复杂逻辑
- 示例：删除确认弹窗、成功提示 Toast

**实战技巧**：如果你在描述弹窗时需要说「这个弹窗里有 5 个输入框和 3 个校验规则」，那它应该是辅助页面；如果只需说「点确认就删除」，那它是简单弹窗。

### 2.4 业务规则的描述层次

**❌ 过于技术化**：
```
"调用 /api/order/create 接口，传 orderId 和 items 数组，
返回 200 则成功，400 则校验失败"
```

**✅ 业务语义**：
```
"创建订单时：
- 输入：订单基本信息（商品列表、收货地址、支付方式）
- 校验：商品库存充足、地址完整、支付方式可用
- 输出成功：订单号、预计送达时间
- 输出失败：库存不足 / 地址不在配送范围 / 支付方式不支持"
```

**为什么**：需求包（01-需求规格说明书.md）禁止写接口定义和技术实现，只描述业务行为。技术实现由 architect-agent 在 03-技术规格说明书.md 中完成。

## 3. 工程组织最佳实践

### 3.1 何时新建工程 vs 纳入已有工程

**新建工程**：
- ✅ 完全不同的业务领域（如电商后台 vs OA 审批）
- ✅ 不同的角色权限体系（角色定义完全不同）
- ✅ 不同的 UI 标准和术语体系

**纳入已有工程**：
- ✅ 业务领域相同，功能扩展
- ✅ 角色权限体系复用或扩展
- ✅ 术语和 UI 标准一致

**实战技巧**：如果你的需求中 80% 的术语（角色、实体、操作）在某个已有工程的 `产品通用规则.md` 中已定义，那应该纳入该工程。

### 3.2 产品通用规则的维护时机

**何时抽取到 `产品通用规则.md`**：
- ✅ 同一术语在 2 个以上任务中出现
- ✅ 同一角色定义在多个任务中复用
- ✅ 同一业务规则适用于多个场景
- ✅ 全局 UI 标准（如颜色规范、间距标准）

**何时保留在任务文档**：
- ❌ 仅本任务使用的特有实体
- ❌ 仅本任务使用的一次性规则
- ❌ 实验性功能（未确定是否推广）

**实战技巧**：第一个任务可以全部写在任务文档中，第二个任务开始时再抽取通用部分。

### 3.3 跨任务影响研判的处理

**场景**：新任务涉及修改已有任务的功能。

**推荐流程**：
1. **明确告诉 agent 关联关系**：
   ```
   "本次任务会扩展 {已有任务名} 的用户管理功能，
   新增「批量导入用户」能力"
   ```

2. **等待 agent 完成 Step 2.5 研判**：
   - Agent 会读取关联任务的 01/02 全文
   - 输出影响分析（复用/扩展/变更三分类）
   - 给出书面方案建议

3. **确认授权（仅变更类需要）**：
   ```
   如果是「变更」类（改/删既有 FR），agent 会请求授权：
   "将改动任务 X 的以下内容：
    - 01 §7 FR-5（原「单个创建用户」改为「单个/批量创建用户」）
    - 02 页面[3] 功能组件（新增批量导入按钮）
   是否授权？"
   
   你回复：「授权」
   ```

4. **双任务留痕**：
   - 关联任务的 01/02 小版本号 +1
   - 两个任务的操作记录都会追加「跨任务联动修改」条目

**实战技巧**：如果只是「引用」已有功能（如「登录页复用已有的验证码组件」），属于「复用」类，无需改关联任务文件，agent 只会在方案中说明引用关系。

## 4. 版本管理最佳实践

### 4.1 小版本号 vs 大版本号

**小版本号 +1**（v1.0 → v1.1）：
- ✅ 新增/修改/删除功能点（FR-x）
- ✅ 页面布局或交互调整
- ✅ 业务规则变更
- ✅ 非功能需求（NFR）指标调整
- ✅ 工程公共规则增量补充

**大版本号 +1**（v1.x → v2.0）：
仅当**结构性重构**时触发（需满足≥2 条）：
1. 新增≥2 个一级业务场景，或核心场景叙事流重设计
2. 角色权限体系发生本质变化
3. 核心流程重设计（主业务链路的节点/分支/状态机结构性调整）
4. 工程归属变更

**实战技巧**：
- 日常迭代 99% 是小版本号 +1
- 只有「推倒重来」级别的改动才是大版本号 +1
- 如果犹豫「算不算大版本」，那就是小版本

### 4.2 操作记录的写法

**标准四字段**：
```
- 计划时间：2026-09-02 14:30
  执行内容：新增 FR-12（批量导入用户）+ 调整页面[3] 布局
  执行结果：01 §7 新增 FR-12 条目 / 02 §4 页面[3] 新增导入按钮
  复核结果：一致
```

**实战技巧**：
- 「执行内容」写**决定要做什么**（目标）
- 「执行结果」写**实际产生了什么产物**（结果）
- 「复核结果」写**结果与目标是否一致**（自检）

## 5. 技术分析智能体（architect-agent）最佳实践

### 5.1 何时调用 architect-agent

**推荐时机**：
- ✅ 需求包（01+02）定稿后，在决策门禁中选择「② 技术分析智能体」
- ✅ 需求包有重大修改（如新增核心 FR、业务规则变化）后，联动更新技术设计

**不推荐**：
- ❌ 需求还在讨论中就调用（会导致技术设计频繁变动）
- ❌ 仅 UI 调整（不涉及功能变化）就联动更新技术设计

### 5.2 技术通用规则的复用

类似 `产品通用规则.md`，architect-agent 也有 `技术通用规则.md`（工程级技术标准）：
- ✅ 跨任务通用的接口规范（如统一的错误码体系）
- ✅ 跨任务通用的数据模型（如用户表、权限表）
- ✅ 跨任务通用的技术约束（如数据库选型、鉴权方案）

**实战技巧**：第一个任务的技术设计完成后，architect-agent 会抽取通用部分到 `技术通用规则.md`，后续任务自动复用。

### 5.3 需求侧与技术侧的版本对齐

**场景**：需求包从 v1.0 → v1.1，技术设计也需要同步更新。

**推荐做法**：
1. 需求包修改完成后，在决策门禁中告诉 agent：
   ```
   "需求包已更新到 v1.1，请联动更新技术设计"
   ```

2. Agent 会检测到 `tech/` 子目录已存在，提示是否调用 architect-agent

3. architect-agent 更新后，技术文档小版本号同步 +1（v1.0 → v1.1）

4. 两侧操作记录都会追加「需求变更联动更新」条目

**实战技巧**：需求侧和技术侧的版本号应保持同步（都是 v1.1），方便追溯对齐。

## 6. 原型生成（Pencil）最佳实践

### 6.1 何时启用原型生成

**推荐场景**：
- ✅ 需要向非技术干系人演示功能（产品经理、客户）
- ✅ 需要视觉验证复杂交互流程
- ✅ 需要导出给 UI 设计师参考

**不推荐**：
- ❌ 仅为了「看起来专业」（需求包（01+02）已足够专业）
- ❌ 功能还在频繁变动中（原型跟不上需求变化）

### 6.2 Pencil 启动前的检查清单

```bash
# 1. 确认 Pencil 桌面应用已打开
ps aux | grep -i pencil

# 2. 确认 Pencil MCP 服务已启动
# （agent 会自动检查，如果失败会提示你）

# 3. 准备好 UI 设计要素（可选）
# 如果有品牌色、字体等要求，提前准备好
# Agent 会引导你填写或使用模板
```

### 6.3 原型自校验的理解

**Agent 会自动执行**：
1. 生成原型后截图（保存到 `screenshots/`）
2. 对比 02-UI交互规格说明书.md 检查偏差
3. 自动修复偏差（宽度/间距/对齐等）
4. 再次截图（保存到 `screenshots-reviewed/`）
5. 输出校验报告（`校验报告.md`）

**你不需要**：
- ❌ 手动截图对比
- ❌ 手动修复原型
- ❌ 担心遗漏细节

**实战技巧**：最终检查 `screenshots-reviewed/` 目录的截图，如果视觉符合预期，原型就可以交付了。

## 7. 故障排查最佳实践

### 7.1 上下文恢复失败

**症状**：Agent 说「不清楚当前工程」或「找不到任务目录」。

**解决方案**：
```bash
# 1. 运行自检
./scripts/context-recovery-check.sh

# 2. 如果检查失败，手动告诉 agent
"我要继续 {工程名} 下的 {任务名} 任务，
 任务目录是 document/{工程名}/{任务名}_{YYYYMMDD}/"

# 3. Agent 会重新加载上下文并复述约束
```

### 7.2 门禁卡住（agent 不进入下一阶段）

**症状**：阶段 1 已完成，但 agent 不进入阶段 2。

**可能原因**：八项判据未全部确认。

**解决方案**：
```
"请检查阶段 1 八项判据，哪些未确认？"

Agent 会列出：
✅ 端与功能类型
⏳ 业务场景（场景[Sx] 未明确）
...

然后补充未确认的信息
```

### 7.3 跨任务影响研判未触发

**症状**：明明涉及其他任务，但 agent 没有执行 Step 2.5 研判。

**解决方案**：
```
"本次任务会影响 {已有任务名}，请执行跨任务影响研判"

Agent 会立即读取关联任务并输出方案
```

## 8. 性能优化最佳实践

### 8.1 减少重复读取

**❌ 不好的做法**：
每次问问题都重新读取 `产品通用规则.md`。

**✅ 好的做法**：
会话启动时 agent 已读取，直接引用：
```
"根据工程级约束（已读取 产品通用规则.md），
 本页面的角色权限是..."
```

### 8.2 合理使用快照恢复

**场景**：长会话后上下文压缩，部分信息丢失。

**推荐做法**：
```bash
# 1. 找到最近的快照
./scripts/session-state.sh list

# 2. 告诉 agent 从快照恢复
"从快照 snapshot_20260902_143000.json 恢复上下文"

# 3. Agent 会读取快照并恢复工程、任务、阶段信息
```

## 总结：核心原则

1. **场景优先**：先确定业务场景[Sx]，再谈页面和功能
2. **功能优先**：先定义功能点（FR-x），再谈 UI 布局
3. **单一权威源**：每类信息只在一个文件定义，其他引用
4. **门禁驱动**：每个阶段产出经确认再推进
5. **版本追溯**：小版本号 +1 记录每次变更，操作记录可追溯
6. **工程复用**：相同业务领域的任务纳入同一工程，复用公共规则
7. **自检复述**：关键节点 agent 自动复述约束，确保不漏不错

遵循这些最佳实践，可以显著提升需求梳理的效率和质量。
