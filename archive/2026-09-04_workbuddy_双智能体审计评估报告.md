## 三、工程链路完整性评估

### 3.1 主干链路（✅ 自洽）

```
prototype-agent（第一环）          architect-agent（第二环）          编程智能体（第三环）
  需求分析                         需求翻译 + 模块归纳                  代码实现
  ↓                                ↓                                 ↓
  prd/                             tech/                             代码仓库
  00-系统概览.md                    common/系统技术规范.md
  common/通用规则×3                 common/数据表设计约定.md
  modules/*/01-需求规格.md          modules/*/03-技术规格.md
  modules/*/02-UI交互规格.md        modules/*/04-数据模型.md
                                  00-系统技术架构总览.md
                                  模块间接口依赖清单.md
```

- 两智能体共享同一 `{系统名}` 目录锚点，但**数据流物理隔离**（prd/ vs tech/），互不污染——设计正确。
- `交接索引.md` 汇总两侧产物作为编程智能体输入清单——链路末端有收口。
- FR-x 作为唯一脊柱键贯穿四层（01 功能 ≡ 02 功能组件 ≡ 03 功能点 ≡ 研发代码功能）——追溯性设计优秀。
- 实际产物验证：食堂订货服务平台的 FR 编号**全局连续唯一**（登录 FR-1/2、商城 FR-3~7、订单 FR-8/9/10），证明脊柱键在实际执行中落地正确。

### 3.2 闭环断裂点（❌ 4 处结构性断裂）

#### 断裂 1：01 章节号体系错位（architect 读上游会「找不到内容」）

- **现状**：prototype 已迁移到**模块级 10 章模板**——`templates/prototype-agent/module-level/01-模块-需求规格.md` 结构为 §1 模块定位 → §2 功能要点（FR-x）→ §3 业务实体 → §4 业务规则 → §5 输入 → §6 输出 → §7 校验 → §8 处理流程 → §9 异常 → §10 未决项。
- **矛盾**：architect 侧的 `spec-analysis` skill、`self-check` skill、`AGENTS.architect.md` 仍引用**旧 14 章单文件体系**的章节号：
  - `spec-analysis` Step 1 写「功能要点清单（FR，含所属场景，01 §7）」「业务规则（01 §9）」「输入（01 §10）」「输出（01 §11）」「校验（01 §12）」「异常（01 §13）」「未决项（01 §14）」
  - `self-check` 写「01 §6–§14 引用（异常 = §13、未决项 = §14）」「列出 01 §7 全部 FR-x」
- **后果**：architect 按 §13 去 01 里找「异常」，但模块级 01 只有 10 章（异常在 §9、未决项在 §10），**§13/§14 根本不存在**。FR-x 追溯、场景覆盖、异常承接等自检全部失效。这是**最严重**的链路闭环断裂。

#### 断裂 2：03 技术规格「承诺结构」与「模板/产物」脱节

- **指令承诺（A 方案）**：`CLAUDE.architect.md` 阶段 2、`AGENTS.architect.md` 阶段 2、`agent/architect-agent.md` 均描述 03 为「**模块 → 功能点两层**，模块定义/边界段 + 每个功能点（FR-x）展开 **9 子项**：①功能描述 ②输入 ③校验 ④处理逻辑 ⑤输出 ⑥异常 ⑦接口契约（OpenAPI）⑧接口初步规划（伪代码）⑨关联数据」。
- **模板/产物（B 方案）**：`templates/architect-agent/module-level/03-模块-技术规格.md` 实际是 **5 节**：§0 架构约束引用 → §1 需求与接口映射（FR→TFP）→ §2 对外接口清单 → §3 关键业务流程 → §4 跨模块依赖 → §5 版本记录。**没有 9 子项结构，也没有模块划分总览**。实际产物 `03-登录模块-技术规格.md` 与模板一致（5 节）。
- **后果**：architect 按指令写 9 子项、按模板写 5 节，两套结构互不兼容；下游编程智能体拿到的 03 缺少「⑦接口契约机器可读 schema + ⑧伪代码」这两项核心承诺，**接口契约内联的诉求落空**。

#### 断裂 3：运行时 prompt（opencode.json）与主指令冲突

- `opencode.json` 是**实际加载运行的 agent prompt**，但它描述的是**旧单文件流程**：
  - prototype prompt：「创建 01-需求规格说明书.md（含 §2.4 场景总览）与 02-UI交互规格说明书.md」——旧单文件，与新「00-系统概览 + modules/*/01-*.md」冲突。
  - architect prompt：「写 tech/03-技术规格说明书.md」「写 tech/04-数据模型说明书.md」——旧单文件，与新「modules/*/03-*.md + 04-*.md 分层」冲突；且描述「9 子项」与模板 5 节冲突。
  - architect prompt 第 7 条：「CLAUDE.md 与 AGENTS.md 是 prototype-agent 的指令文件，与本智能体无关」——**错误断言**：CLAUDE.md 内的「术语对照表」是四层模型唯一权威源，architect 的 skill 均引用 `CLAUDE.md §术语对照表`。此断言会误导 architect 不去读术语权威源。
- **后果**：运行时 agent 会按旧单文件流程执行，与主指令（CLAUDE.md / CLAUDE.architect.md）的模块化流程产生行为分叉。

#### 断裂 4：模板文件命名/路径错位（首次创建「复制模板」会失败）

- `tech-architecture` skill 引用 `templates/architect-agent/system-level/common/系统技术规范.md`（**不存在**，无 common 子目录）与 `templates/architect-agent/system-level/00-系统技术架构总览.md`（**不存在**）。
- `data-model` skill 引用 `templates/architect-agent/system-level/common/数据表设计约定.md`（**不存在**）。
- `tech-common-rules` skill 引用 `templates/技术通用规则.md`（**不存在**，实际内容错位在 `system-level/系统级技术标准.md`）。
- **后果**：architect 各阶段「从模板复制填占位符」的首建动作会因找不到模板而失败。

### 5.1 优点（设计层）

1. **「需求翻译器/中转站，不做架构设计」定位精准**：模块归纳（需求翻译）允许、分层/选型/部署（架构设计）禁止——边界清晰，避免 LLM 越界。

4. **机器可读优先 + 伪代码保可译性**：接口契约（schema/状态码/错误码）+ 伪代码双轨并行，兼顾可消费与可译。
5. **「生成中遇不确定即停」硬规则**：3 种触发情形，禁止臆造、禁止标「待确认」出稿。

## 六、链路闭环专项诊断

### 6.1 门禁闭环（✅ 基本完整）

- prototype：门禁 1（系统架构）→ 门禁 2（逐模块）→ 决策门禁（三选一）——闭环完整。
- architect：门禁 0（技术通用规则）→ 门禁 1（需求解析）→ 门禁 2（技术规格）→ 门禁 3（数据模型）→ 收口——闭环完整。
- **但**：门禁 1/2/3 前的 self-check 引用了废弃章节号（断裂 1），导致「自检」这道安全网实际失效——门禁框架在，但门禁内的校验逻辑断链。

### 6.2 版本联动闭环（✅ 设计完整，⚠️ 命名漂移）

- 小版本号 +1 规则：prototype 更新 → architect 小版本号同步 +1，双向联动，设计完整。
- 但版本记录文件的命名（prd-任务操作记录 vs prd-系统操作记录、技术工程摘要 vs 技术项目摘要）漂移，导致「记入哪个文件」存在歧义。

### 6.3 交接闭环（⚠️ 模板是旧版）

- `templates/交接索引.md` 仍是**旧单文件版**：引用 `prd/01-需求规格说明书.md`、`tech/03-技术规格说明书.md`（单文件），与模块化架构不符。
