- **① 功能描述**: [一句话说清这个功能做什么，来源 01 §6 用户故事 + §7 功能要点 + §6 验收标准；关联页面[1]/功能组件]
- **② 输入内容**:
  - 字段 / 来源 / 类型 / 必填 / 默认 / 约束
  - 例：`date` 来自 Query，date，否，今天，仅年月日
  - 例：`user_id` 由 JWT 在接入层注入，不出现在请求体
- **③ 校验规则**:
  - 例：`days` 正整数且 ≤ 90；`limit` ≤ 20（语义校验，机器可读描述）
- **④ 处理逻辑**（含复杂逻辑 / 状态机 / 算法，原 06 内容并入此处）:
  - 例：按 `(user_id, date)` 聚合 `t_sport_record`，按 `sport_type_id` 分组累加 `duration/distance/calories`；近 N 天按日序列；最近 N 条取最新。
  - 复杂功能在此展开时序 / 状态机 / 关键算法。
- **⑤ 输出内容**:
  - 字段 / 类型 / 说明（成功态）；例：`cards[]`(分组聚合) + `summary`(总次数/时长/卡路里)
  - 失败态仅记语义映射（见 01 §11），视觉呈现归 02。
- **⑥ 异常处理**（功能点级业务处理策略，从 01 §13 承接）:
  - 例：并发连点 → 幂等保证仅生成一笔；外部超时 → 记录草稿并提示重试；数据中途失效 → 中止并提示。
  - 仅写**业务处理策略**（重试/幂等/补偿/降级），传输层错误码见「⑦ 接口契约」，两者交叉引用不重复。
- **⑦ 接口契约**（端点 / 方法 / 请求响应 schema / 错误码，机器可读，供下游精确对接）:
  - `GET /api/v1/sport-records/today`
  - 鉴权: JWT（注入 user_id）
  - 请求 schema: `无 body；Query: date?=YYYY-MM-DD`
  - 响应 schema:
    ```json
    { "code":0, "data": { "date":"2026-07-08", "cards":[ { "sportTypeId":1, "totalDurationMin":70, "totalCalories":640, "count":2 } ], "summary": { "totalCount":2, "totalCalories":640 } } }
    ```
  - 状态码: 200 / 401
  - 异常处置（错误码）:
    | HTTP | code | message | 触发场景 | 处置 |
    |------|------|---------|---------|------|
    | 401 | 10002 | 未授权 | 缺/失效 JWT | 要求登录 |
  - 并发需求: 只读聚合；热数据缓存；无写冲突（基线见技术通用规则 §1）
- **⑧ 接口初步规划（伪代码）**（给研发直接翻译；表达处理函数签名 + 步骤，**不写具体框架/ORM 调用**，守中转站定位）:
  ```
  function getTodaySport(userId, date=today) -> TodaySportView:
      records = query t_sport_record where user_id=userId and day(created_at)=date   # 见 04
      cards = groupBy(records, sport_type_id).map(sum duration/distance/calories)
      summary = { totalCount: records.count, totalCalories: sum(calories) }
      return { date, cards, summary }
  ```
