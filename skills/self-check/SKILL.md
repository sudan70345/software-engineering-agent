## 自检内容（七类检查 · 按门禁差异化范围）

### 检查 1：FR-x 追溯矩阵

> 目标：FR-x 为唯一脊柱键，须在四层间无遗漏、无重复、无悬空。
> FR-x 编号规则：模块内从 FR-1 起编、连续唯一，全局以「模块名+FR-x」组合定位（不跨模块全局连续编号）；追溯矩阵的键 = 「模块名+FR-x」。

- **门禁 1**（01↔02）：
  - 列出 01 §2 全部 FR-x。
  - 逐条核对每个 FR-x 在 02 §4 是否有对应功能组件（02 §4 功能组件应标注承载的 FR-x）。
  - 输出：`FR-x | 01 §2 | 02 功能组件 | 状态✅/❌`。
- **门禁 2**（01↔02↔接口契约↔03↔05）：
  - 在门禁 1 基础上追加：01 每个 FR-x 是否在 03 §1「模块定义与功能点映射」表的 FR→TFP 列出现，且**仅归属一个主模块**（跨模块调用在接口清单「关联模块」记录，不重复归属）。
  - 反向核对：03 §1 功能点映射表中的每个 FR-x 是否都能回溯到 01 §2（无幽灵 FR-x）。
  - **05 侧反向核对**：05 §1「对应 FR」与 §2「对应 FR」列中的每个 FR-x 是否都能回溯到 01 §2（无幽灵 FR-x）。
    > ⚠️ **05 侧不做正向全覆盖要求**：纯后端 FR-x（定时任务、内部批处理、数据同步、对外回调等）合法地**没有前端落点**，强制「每个 FR 必有 05 落点」会产生系统性误报。前端侧的正向覆盖由**检查 4a**承担——覆盖的锚点是「02 的页面」，不是「01 的 FR」。
  - **契约侧核对**：`接口契约.md` §3 契约明细中每个接口的「对应 FR」是否都能回溯到 01 §2（无幽灵 FR-x）。
  - **跨模块依赖核对（按部署形态分叉）**：核对 03 §4「跨模块依赖」声明的被依赖模块——
    - **单体部署**（默认，本进程调用）：只核对**被依赖模块确实存在**且与 03 §1「关联模块」一致（**无凭空依赖**）；**不要求** `operationId` 映射——本进程调用不产生 HTTP 接口，`接口契约.md` 中本无对应条目，强行要求会产生**系统性误报**。
    - **已拆服务**（跨进程调用）：被调用的 `operationId` 须 ∈ `接口契约.md` §2 接口总表，且能回溯到该模块 03 §2。
    - **部署形态未明确** → 按**单体**核对并登记 `TECH-OPEN-*`（**不判失败**）。
    - ⚠️ 部署形态属**技术架构**，architect 不决策；**不得为满足本检查而臆造 `operationId`**。
  - 输出：`FR-x | 01 §2 | 02 功能组件 | 03 模块 | 契约 operationId | 05 页面/组件 | 状态✅/❌`。
- **门禁 3**（01↔02↔接口契约↔03↔04↔05）：
  - 在门禁 2 基础上追加：03 §2 各接口的「关联数据」是否在 04 §1 实体与表清单有对应实体；04 每个实体的「所属模块」是否与 03 §1 归纳结果（M1/M2…）一致（实体所属模块继承 03）；`接口契约.md` §3 各接口的「业务上下文」跳转是否都指向存在的 03 §2 接口。
  - 05 侧核对延续门禁 2 范围（05 不直接承载实体，无需追加）。
  - 输出：`FR-x | 01 | 02 | 03 模块 | 04 实体 | 契约 operationId | 05 页面/组件 | 状态✅/❌`。

### 检查 2：场景覆盖矩阵

> 目标：系统要求规范 §2 的每个场景[Sx] 须在下游有体现，无悬空场景。

- **门禁 1**（系统要求规范→01/02）：
  - 列出 系统要求规范 §2 全部场景[Sx]。
  - 核对每个场景是否在 01 §1（模块定位「所属场景」）或 02 §1（页面定位「所属场景」）出现。
  - 输出：`场景[Sx] | 系统要求规范 §2 | 01/02 模块/页面 | 状态✅/❌`。
- **门禁 2**（系统要求规范→01/02→03）：
  - 追加：每个场景是否经其 FR-x 在 03 §1 模块定义段的「关联场景」中体现（场景经 FR-x 多对多关联模块）。
  - 05 不承载场景（05 §1 只有权限角色，无场景列），本检查范围不含 05。
  - 输出：`场景[Sx] | 系统要求规范 §2 | 01/02 | 03 模块 | 状态✅/❌`。
- **门禁 3**：与门禁 2 范围一致（04 不直接承载场景，无需追加）。

### 检查 3：章节号 / 引用 / 术语一致性

> 目标：跨文档引用准确、术语用法与唯一权威源一致，无旧术语残留。

适用门禁 1/2/3（每次产出新文档后都对全部已存在文档做一遍）：

- **章节号引用**：本阶段产出文档中对其他文档的章节号引用，与目标文档实际章节号逐一核对（以本节顶部「章节号基准」为唯一权威）。重点：
  - 03 §0 对 `系统级技术标准.md` 的引用（§1 并发容量 / §2 命名与规范约定 / §3 跨模块统一约定 / §4 通用领域模型 / §5 技术基线引用 / §6 变更）。
  - 各文档对 01 §1–§10 的引用（功能=§2、业务规则=§4、输入=§5、输出=§6、校验=§7、异常=§9、未决项=§10，这是既有审计发现的高错点）。
  - 04 对 03 §1/§2 与 03 §2「查询语义」的引用（§4 只写并发**业务场景**）；**05 §0/§1–§8 对 02 §1（页面定位）/§4（功能组件）/§5（关键交互）/§6（页面状态变体）/§7（页面流转）与 01 §7（校验规范）的引用**。
  - 对 `接口契约.md` 的引用（§2 接口总表 / §3 契约明细 / §4 错误码总表）——**错误码清单与接口清单的权威源均在此，不得指向 03 §2 或 系统级技术规范 §4/§12**。
  - 系统要求规范 §6.3「端范围」的引用（05 §7 平台差异的判定依据，写法为 `§6.3`）。
- **术语一致性**：检查术语三件套（`功能组件` / `模块` / `代码模块`）与 `场景[Sx]` / `页面[N]` / `辅助页面[N-A]` 等术语在产出文档中用法是否与 `CLAUDE.md §术语对照表` 一致，**无旧术语残留**（已知旧术语：`功能模块`、`接口规划`、`05-接口设计`、`06-模块详细设计`、`工程`/`任务`[已统一为 项目/系统]、`00-系统概览`/`00 §N`[已统一为 系统要求规范]）。
  - **05 专属口径**：`页面[N]` / `辅助页面[N-A]` 的编号必须与 02 **完全一致**（不得在 05 重编号）；接口一律以 `operationId` 指称，**不得出现接口编号别名**（如 `I-1` 与 operationId 混用）。
  - **契约专属口径**：`operationId` 只登记在 `接口契约.md` §2；`03` §2 与 `05` §4 引用时必须与契约登记**逐字一致**（大小写敏感）。
- **跨文档引用**：文档间引用的文件名、相对路径是否正确。**tech 侧模块级文件（03 / 04 / 05，位于 `tech/modules/{模块}/`）的基准路径（唯一权威）**：
  - → `tech/` 系统级文件（`系统级技术标准.md` / `系统级技术规范.md` / `数据表设计约定.md` / `接口契约.md` / `代码工程结构说明.md`）：`../../`（**2 级**）
  - → `{系统}/prd/...`（`系统要求规范.md`、模块 `01` / `02`）：`../../../prd/`（**3 级**）
  - → 项目级通用规则（`通用异常处理.md` / `通用校验规则.md`）：`../../../../`（**4 级**）
  - 同级模块文件互引（03 ↔ 04 ↔ 05）：直接写文件名，**不加任何路径前缀**
  - **契约文件内**引用模块文件：`modules/{模块}/03-{模块}-技术规格.md`（相对 `tech/` 根，不加前缀）
  > ⚠️ **本项为已知高发错误点**：模块级文件对系统级的引用常被误写为 1 级（`../系统级技术标准.md`）、对 prd 的引用常被误写为 2 级（`../../prd/...`）——**两者均为死链**（会指向 `tech/modules/...` 与 `tech/prd/...`，均不存在），必须逐条实盘验证。
- 输出：问题清单 `位置(文件§节) | 问题类型(章节号/术语/引用) | 描述 | 修复建议`。

### 检查 4：前端侧一致性（05 ↔ 01 / 02 / 接口契约）

> 目标：`05` 是前端（含移动端）的**唯一权威定义**，须与上游「页面（02）/ 规则（01）/ 接口（契约）」在**覆盖、引用、分工、边界**四个方向无漂移。
> 适用门禁：**2 / 3**（05 与 03 同轮产出，门禁 2 起即有 05 可校）。门禁 1 无 05，本检查跳过。

- **4a 页面覆盖（02 §1 ↔ 05 §1 ↔ 05 §8）**
  - **正向**：02 §1 的每个主页面[N] 与辅助页面[N-A] 是否都在 05 §1「页面与路由」表出现，且已声明 路由 path / 页面类型 / 可见角色 / 进入参数 / 路由守卫。
  - **反向**：05 §1 的每一行是否都能回溯到 02 的某个 页面[N]/[N-A]（**无凭空新增页面**）。
  - **属性一致**：05 §1「页面类型」须与 02 §1 标注一致（主页面 / 辅助页面）；辅助页面须标注所属主页面；页面编号须与 02 完全相同。
  - **落点收口**：05 §1 的每个页面须在 05 §8「前端落点」有对应行（含前端工程 + 目录/文件），**无空槽位**。
  - 输出：`页面 | 02 §1 | 05 §1 路由 | 类型一致 | 05 §8 落点 | 状态✅/❌`。
- **4b 接口引用闭合（05 §4 → 接口契约）**

### 检查 6：逻辑自洽性（03 §3 逻辑单元 ↔ 03 内部 / 04 字段）

> 目标：从「**文档之间引用对不对**」进到「**逻辑本身对不对**」——上一阶段一致性只校验跨文档引用，本检查校验逻辑的内部完整性。

- **6f 逻辑 ↔ 数据字段级引用有效（仅门禁 3）**——03 §3 逻辑体 / §2 校验语义中引用的**实体与字段**须在 04 §1 / §2 存在（**无幽灵字段**）；反向：04 每个业务字段至少被一个逻辑单元或接口引用（无凭空字段）。

## 边界

- 本 skill **只做一致性自检**，不做架构评审、合规复核、技术架构风险审核、技术架构设计关键链路覆盖度审查——这些不在 architect-agent 职责内（architect 定位为「需求翻译器 / 中转站，不做架构设计」，见 `CLAUDE.architect.md` 核心约束）。
- **检查 4 同样只做「一致性」，不做 UI / 交互评审**：它校验的是「05 与 01/02/契约对不对得上」（覆盖、引用、分工、边界），**不评判**页面设计好坏、交互合理性、视觉还原度——那些属产品 / 设计评审，不在本 skill 范围。
- **检查 5 只校验「业务语义 ↔ 索引落点是否对齐 + 全文档有无越界写外部技术架构内容」**，**不评判**索引设计优劣、SQL 性能、是否需要缓存或分库分表、技术选型是否合理——那些属外部技术架构与工程基线决策。
- 本 skill **不产出独立文档**，结果只写入 `tech-系统操作记录.md` 的复核字段。
- 本 skill **不替代门禁**：自检通过后仍须请用户确认门禁；自检是「专业维度补盲」，门禁是「用户决策确认」，两者互补。
