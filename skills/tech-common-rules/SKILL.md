# 系统级技术标准确认 Skill — 阶段 0（门禁 0）

## 🛡️ 执行前自检（必做）

执行本 Skill 前必须确认：
1. ✅ 已完成项目归属判定（项目名明确）
2. ✅ 当前系统目录明确（`document/{项目名}/{系统名}/tech/`）
3. ✅ 本 Skill 产出文件归属正确（系统 `tech/` 子目录 系统级技术标准.md）

**若任一项不确定 → 立即执行「CLAUDE.architect.md §上下文恢复检查点」R1-R4 流程。**

## 定位
本 Skill 是 architect-agent 的**第 0 阶段**，位于「项目归属判定」之后、阶段 1（spec-analysis）之前。
职责：确保**系统级** `系统级技术标准.md` 在生成任何模块级技术设计文档（03/04/05）之前已**建立并经用户确认**，并在全流程中持续维护这一单一权威源。

> 📌 **本阶段不做架构设计**：architect 定位为需求翻译器 / 中转站。**编程语言 / 框架中间件 / 系统分层 / 部署形态 / 非功能性技术设计**属**外部技术架构**，由工程基线（工程仓库的构建与部署配置文件、CI、代码风格配置）承载，本阶段只**登记引用**（见 Step 2 第 E 类），**不逐项设计、不臆造选型**。
> 📌 **判据（唯一）**：**换成别的技术栈，结论会不会变？** 会变 → 外部技术架构 / 技术策略 / 技术配置 → 工程基线承载，本阶段不产出；不变 → 业务语义 / 跨模块统一约定 → 本文件承载，必须写。
> 📌 技术规则约定**不设项目级「技术通用规则」**：业务约束与跨模块统一约定下沉至系统级 `系统级技术标准.md`；技术目标（模块 / 接口 / 表 / 性能指标）落在 `系统级技术规范.md`；数据表统一约定（系统默认字段 / 软删除过滤）独立为 `数据表设计约定.md`。

## 何时触发
- **入口触发**：项目归属判定已确定 `{项目名}`、系统目录 `{系统名}` 明确（新建系统 或 纳入已有系统）之后，立即触发，再进入阶段 1。
- **持续触发**：阶段 1~4 或任何后续对话中，一旦出现新的统一约定项，随时回写（见 Step 4）。

## 输入
- 项目归属判定结果（新建 / 纳入；项目目录路径、系统目录路径）
- 若纳入已有系统：现有 `document/{项目名}/{系统名}/tech/系统级技术标准.md`
- **工程基线**（如可得）：既有的语言 / 框架 / 分层 / 部署 / 非功能技术方案（来自工程仓库配置文件或用户给定）

## 输出
- `document/{项目名}/{系统名}/tech/系统级技术标准.md`（初始化或维护后）
- 用户对标准内容的确认（门禁 0）

## 工作流程

### Step 1：判定标准文件是否存在
检查 `document/{项目名}/{系统名}/tech/系统级技术标准.md`：
- **不存在 → 走 Step 2（初始化问卷）**
- **已存在 → 走 Step 3（缺口检查与确认）**

### Step 2：初始化问卷（标准文件不存在）
逐项向用户**询问并确认**以下内容（不可自行臆造；含糊处必须反问，禁止硬编）。

**A. 并发与容量目标（业务侧）** → §1
- 日活 / 数据量级（如 DAU 5w、核心表年增量）
- 峰值 QPS / TPS（**业务流量预期**，非技术方案）
- 一致性要求（强一致 / 最终一致 / 混合）
- 延迟要求（如 P99 < 200ms）
- 可用性目标（如 99.9%）
> ⚠️ 此处收集的是**系统整体业务基线**，所有接口默认以此为准；单个接口的特殊高并发场景（超出基线）在模块级 03 的接口业务上下文中逐接口确认。
> ⚠️ **容量规划手段**（分库分表 / 冷热分离 / 限流实现）属外部技术架构，**不在此收集**。

**B. 命名与规范约定** → §2
- 数据库命名（表名 / 字段名 snake_case；主键；审计字段；软删字段）
- 接口命名（RESTful、kebab-case、资源名复数；响应包络与字段映射指向 `接口契约.md`）
> ⚠️ 代码风格 / 提交规范 / 构建配置属工程基线，不在此收集。

**C. 跨模块统一约定** → §3
- 状态码约定、分页约定、排序 / 过滤约定
- 鉴权约定（Header 携带凭证的方式；**鉴权方案选型属工程基线**）
- 软删除约定、审计字段约定、多租户约定
- 幂等业务要求（**哪些操作必须防重复提交**；实现方案属工程基线）

**D. 通用领域模型** → §4
- 跨模块反复出现的业务概念（如 用户、组织、附件）及其通用业务属性

**E. 技术基线引用** → §5（**只登记，不设计**）

> 📌 `代码工程结构说明.md`（槽位定义含所有权）与 `系统级技术规范.md` §15「可运行性元数据」均由**阶段 1 推导产出**，**不属阶段 0 产出范围**——本阶段只登记 §5「技术基线引用」，不产出、不改写这两个文件。
- 请用户提供 / 确认工程基线来源：编程语言与版本、核心框架与中间件、系统分层与模块划分、部署形态与拓扑、非功能性技术设计。
- **若工程基线尚未建立** → 登记 `TECH-OPEN-*` 并在门禁 0 中提出，**禁止本 agent 自行臆造技术选型**。
- 本系统对基线的引用备注（如「遵循后端服务脚手架」「参考工程基线依赖清单」）。

按 `templates/architect-agent/system-level/系统级技术标准.md` 起草全文，**展示全文请用户确认（门禁 0）**。确认后写入 `document/{项目名}/{系统名}/tech/系统级技术标准.md`，并在末节变更记录追加「初始化」行。

> 模板参见 `AGENTS.architect.md` 门禁 0 问卷与确认模板。

### Step 3：缺口检查与确认（标准文件已存在）
读取现有标准，逐项核对 A~E 五类是否齐全，**重点检查「A. 并发与容量目标」是否缺失或过期**：
- 齐全 → 列出「已确立要点」请用户确认后进入阶段 1。
- 有缺口（尤其并发容量基线）→ 列出缺口，请用户补全（走问卷相关项），更新文件 + 变更记录，再进入阶段 1。
- **若现有标准仍含架构设计内容**（语言 / 框架 / 分层 / 部署 / 非功能的具体选型、代码 / 提交规范、字符集 / 引擎 / 字段类型 / 索引命名 / 锁策略）→ 按判据**收窄**：迁出为「技术基线引用」（§5）或删除，并在变更记录留痕。
- **禁止在未经确认的情况下，仅凭猜测把选型写进标准文件。**

### Step 4：持续更新机制（贯穿全流程 + 后续对话）
**硬规则**：在阶段 1~4 或任何后续对话中，一旦出现**新的统一约定项**（新增命名约定、分页 / 鉴权 / 软删 / 审计 / 多租户约定、新错误码段、通用实体、新并发容量要求等），必须：
1. 立即回写对应系统级文件：业务约束与统一约定 → `系统级技术标准.md`；技术目标 → `系统级技术规范.md`；数据表统一约定 → `数据表设计约定.md`。
2. 在对应文件变更记录追加一行（时间 / 来源对话 / 更新内容）。
3. 在回复中告知用户「已更新系统级技术标准（或规范）：xxx」。
> ⚠️ **不得**把技术架构选型（语言 / 框架 / 分层 / 部署 / 锁策略 / 缓存 TTL 等）回写为本文件内容——那属工程基线。

各阶段 Skill（tech-architecture / data-model）在产出时如发现此类项，须在收尾时执行本步。

## 前置条件
- 项目归属判定已完成（已确定 `{项目名}`）。
- 系统目录 `{系统名}` 已明确（若系统目录尚未确定，须先与用户确认系统名后再初始化标准文件）。

## 门禁
- **门禁 0**：`系统级技术标准.md` 内容必须经用户确认（初始化或缺口补全）后，方可进入阶段 1（spec-analysis）。标准文件未确认前，禁止生成 03/04/05。
