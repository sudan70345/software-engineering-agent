# 技术通用规则确认 Skill — 阶段 0（门禁 0）

## 定位
本 Skill 是 architect-agent 的**第 0 阶段**，位于「工程归属判定」之后、阶段 1（spec-analysis）之前。
职责：确保工程级 `技术通用规则.md` 在生成任何技术设计文档（03/04/05）之前已**建立并经用户确认**，并在全流程中持续维护这一单一权威源。

## 何时触发
- **入口触发**：工程归属判定已确定 `{工程名}`（新建工程 或 纳入已有工程）之后，立即触发，再进入阶段 1。
- **持续触发**：阶段 1~5 或任何后续对话中，一旦出现新的通用标准项，随时回写（见 Step 4）。

## 输入
- 工程归属判定结果（新建 / 纳入；工程目录路径）
- 若纳入已有工程：现有 `../技术通用规则.md`

## 输出
- `../技术通用规则.md`（初始化或维护后）
- 用户对规则内容的确认（门禁 0）

## 工作流程

### Step 1：判定规则文件是否存在
检查 `document/{工程名}/技术通用规则.md`：
- **不存在 → 走 Step 2（初始化问卷）**
- **已存在 → 走 Step 3（缺口检查与确认）**

### Step 2：初始化问卷（规则文件不存在）
逐项向用户**询问并确认**以下标准化信息（不可自行臆造；含糊处必须反问，禁止硬编）：

1. **技术语言（含版本）**：后端 / 前端 / 脚本语言与版本（如 Java 17 / TypeScript 5.x / SQL MySQL 8.0）。
2. **数据库（含版本与形态）**：主存储类型与版本；是否分库分表、读写分离、JSON/扩展字段支持。
3. **技术框架 / 中间件**：Web 框架、ORM、缓存、MQ、对象存储、网关、多模态等及版本。
4. **并发要求（容量目标）**：峰值 QPS / TPS、日活与数据量级、一致性要求（强一致 or 最终一致）、延迟要求（P99）、可用性目标、容量规划。⚠️ 此处收集的是**项目整体基线**，所有接口默认以此为准；单个接口的特殊高并发场景（超出基线、额外幂等/锁/限流策略）在 03-技术规格说明书 的接口契约中逐接口确认。
5. **技术规范**：代码规范、API 规范（RESTful / 响应包络 / 命名）、数据库规范（命名 / 主键 / 审计 / 软删）、提交规范、注释与文档要求。

按 `templates/技术通用规则.md` 起草全文（含 §1 并发与容量目标），**展示全文请用户确认（门禁 0）**。确认后写入 `../技术通用规则.md`，并在 §10 维护记录追加「初始化」行。

> 模板参见 `AGENTS.architect.md` 门禁 0 问卷与确认模板。

### Step 3：缺口检查与确认（规则文件已存在）
读取现有规则，逐项核对上述 5 类是否齐全，**重点检查「并发要求（§1）」是否缺失或过期**：
- 齐全 → 列出「已确立要点」请用户确认后进入阶段 1。
- 有缺口（尤其并发要求）→ 列出缺口，请用户补全（走问卷相关项），更新文件 + §10 维护记录，再进入阶段 1。
- **禁止在未经确认的情况下，仅凭猜测把选型写进规则文件。**

### Step 4：持续更新机制（贯穿全流程 + 后续对话）
**硬规则**：在阶段 1~5 或任何后续对话中，一旦出现**新的通用标准项**（新增框架/中间件、新规范、新并发要求、新错误码段、新命名/状态机约定、跨任务通用实体等），必须：
1. 立即回写 `../技术通用规则.md` 对应节：规范 → §4/§5；通用实体 → §6；并发 → §1。
2. 在 §10 维护记录追加一行（时间 / 来源任务或对话 / 更新内容）。
3. 在回复中告知用户「已更新技术通用规则：xxx」。

各阶段 Skill（tech-architecture / data-model）在产出时如发现此类项，须在收尾时执行本步。

## 前置条件
- 工程归属判定已完成（已确定 `{工程名}` 与目录）。
- 若新建工程：已创建工程目录（规则文件将在此初始化）。

## 门禁
- **门禁 0**：`技术通用规则.md` 内容必须经用户确认（初始化或缺口补全）后，方可进入阶段 1（spec-analysis）。规则文件未确认前，禁止生成 03/04/05。
