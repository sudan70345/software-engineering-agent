## 定位
本阶段是 architect-agent 的**核心枢纽**：把上游需求包（01 的 FR-x）**归纳为模块**并翻译为可直接指导编码的技术规格（模块 → 功能点两层）。**不做架构设计**——技术选型/分层/部署/非功能等属**外部技术架构**，由**工程基线**承载；本阶段只引用 `../../系统级技术标准.md` §5「技术基线引用」，不展开选型。
- ⚠️ **模块归纳 ≠ 架构设计**：把扁平 FR-x 按统一业务逻辑聚合为模块，是「需求翻译」的核心（允许、必做）；决定 service/dao 分层、技术选型、部署拓扑才是架构设计（不做，归**工程基线** / 研发）。
- ⚠️ **模块 ≠ 场景**：01 的场景是业务情境（横切叙事、跨模块）；模块是技术域聚合（围绕核心业务对象的功能簇）。二者经 FR-x 多对多关联，勿把场景当模块。
- ⚠️ **本阶段产出为初步分解**（偏细、可审阅）：架构受限下**宁细勿粗**，最终合并/映射代码模块由后续人员/研发结合真实架构决定，本阶段不越界替其决策。

## 工作流程

### Step 1：归纳模块脊柱（§1 模块划分总览）
读取 `../prd/系统要求规范.md` §5 模块清单 + `../prd/modules/` 目录下所有模块的 01 文件（按需读取），汇总全部 FR-x，按**模块归纳判据**聚合为模块，产出「模块 → FR-x」映射（§1.2 总览表：模块/名称/类型/覆盖能力/含FR-x/待校准）。**每条 FR-x 必须且仅归属一个主模块**，跨模块调用在功能点「关联模块」中记录，不重复归属。禁止遗漏或重复 FR-x（与 01 双向可追溯）。
- **模块归纳判据**（写入 §1.1）：① 主对象归属（FR-x 服务的核心业务对象/能力）；② 同对象聚合为业务域模块（覆盖对象完整 CRUD 生命周期）；③ 跨切面能力独立成模块（鉴权/通知/日志等，被多模块共享且独立演进）；④ 跨对象功能按核心能力归属，调用他模块记为「关联模块」；⑤ 粒度**宁细勿粗**，拿不准就单独成模块。
- **模块类型**：业务域 / 跨切面。

### Step 2：生成系统级标准、规范与契约（先前置）
在开始逐模块展开前，**检查或确认**系统级标准与规范文件：
- **系统级技术标准.md**：确认业务约束与跨模块统一约定是否已确定（阶段 0 已建立）
  - 包含：并发容量业务目标 / 命名与规范约定 / 跨模块统一约定 / 通用领域模型 / **技术基线引用**（语言·框架·分层·部署·非功能归工程基线，本文件不定义）
  - 若不存在或不完整，与用户确认后生成/补全初版
- **系统级技术规范.md**：确认系统级技术目标是否已确定
  - 包含：API 路由前缀、幂等业务要求、缓存业务需求、事务边界（业务视角）、权限隔离、错误码分段规则、性能目标、**§15 自测通过判据（含「可运行性元数据」登记表：构建 / 测试命令 · 测试框架 · 启动顺序 · 端口）**
  - 若不存在，与用户确认后生成初版
- **接口契约.md**：建立 §0 契约总则（权威源与单源形态 / 命名映射 snake_case↔lowerCamelCase / 版本兼容）+ §1 全局约定（统一响应包络 / 分页 / 鉴权 / 幂等）；§2 / §3 / §4 随模块与阶段推进增量填充
- **阶段 1 完成后、逐模块展开前**，这三个文件应已有初版且经确认（契约的 §2 / §3 / §4 允许随模块增量追加）
- **代码工程结构说明.md**（**阶段 1 推导产出，非外部输入**）：**确认** §1 槽位表是否已产出（推导方法见 `skills/spec-analysis`「输出」与该模板头部，**此处不重复**）
  - 已产出 → 作为 03 §3「落点」与 05 §8「前端落点」的**唯一依据**
  - 阶段 1 未产出（异常）→ 按 `templates/architect-agent/system-level/代码工程结构说明.md` 头部的「推导优先 + 差额问询」补做；单项推不出 → 登记 `TECH-OPEN-*`，**禁止臆造代码路径**

### Step 3：逐模块 → 逐功能点展开（核心）
**按模块（M1、M2…）逐个展开**；每个模块生成一个独立的 `03-{模块名}-技术规格.md` 文件。

每个模块文件 = **模块定义/边界段** + 其下若干**功能点块**。

> ⚠️ **生成中遇不确定必须暂停反问（硬规则）**：写接口的处理逻辑（复杂逻辑 / 状态机 / 算法）等时，若业务规则不清、存在多种合理实现、或信息与上游 01/02 及「系统级技术标准/规范」冲突，必须**立即停止并向用户确认后再落笔**；禁止臆造、禁止仅以「待确认」标记直接出稿等门禁 2 时再发现。确认过程记入 `tech/tech-系统操作记录.md`，必要时登记 TECH-OPEN-*。

- **模块定义/边界段**：核心业务对象/能力 · 统一业务逻辑（内聚点）· 聚合的 FR-x · 关联场景（经 FR-x，来自 系统要求规范 §2）· 关联模块（跨模块调用）· 边界说明（本模块不含什么）。
- **功能点块**（= FR-x）：按 `templates/architect-agent/module-level/03-{模块}-技术规格.md` §2「对外接口清单（后端业务上下文）」的结构展开（每接口：`operationId`（引用契约）/ 功能描述 / 校验语义 / **接口编排（引用 `LU-x`）** / **查询语义（仅读接口）** / 异常处置策略 / 关联数据→04）。
  - **接口机器可读定义同步写入契约**：本模块每个接口的端点 / 请求 schema / 响应 schema / 状态码 / 错误码写入 `tech/接口契约.md` §3「{模块名}」分区，并在 §2 接口总表登记 `operationId`（**全局唯一**）；03 §2 **不重复 schema**。
  - **读接口必补「查询语义」**：筛选维度 / 默认排序 / 分页规则 / 过滤条件 / 关联加载语义（**业务语义**）；**不写访问技术方案**（ORM / 分页插件 / 缓存 / 读写分离 / 连接池 / 具体 SQL 实现）。判据：**换技术栈会改变结论的属外部技术架构，本项目不产出**。索引落点在模块 04 §3。
  - **引用系统规范**：系统级的规范通过引用（不复制），只补模块特有的差异
  - ⚠️ 机器可读（schema + 状态码 + 错误码）与伪代码（可译性）须并存，详见模板注释。
- **逻辑单元清单**（§3：本模块**业务逻辑的唯一权威归属地**）：
  - 生成 **§3.1 总表**（`LU-x` / 名称 / 类型[规则·流程·状态机·算法·数据域·校验] / 对应 FR / 被引用 / 落点 / 测试锚点）+ **§3.2 逐单元详述**（目的 / 输入 / 输出 / 前置 / 逻辑体 / 状态迁移表 / 引用 / 被引用 / 落点 / 测试锚点）。
  - **抽取规则**：被 **≥2 处**引用、含**状态机 / 复杂算法 / 跨实体判定**、或作为「统一业务逻辑（内聚点）」出现 → **必须抽为 `LU-x`**；单接口内一次性简单步骤可内联在 §2「接口编排」。
  - **ID 规则**：`LU-x` 模块内从 `LU-1` 起编、连续唯一，全局以「模块名+LU-x」组合定位（与 `FR-x` **同构**）。
  - **落点**必须落在 `../代码工程结构说明.md` §1「槽位定义」内；槽位未定义时登记 `TECH-OPEN-*`。
  - **三条硬约束**：① 引用闭合（无「调用未定义」）② 无孤儿 ③ 命名归一（一个逻辑 = 一行 = 一个 ID）——由 `self-check` 检查 6 校验。

## 逻辑体语法子集（受控伪代码）

> 表达法**分层**：03 §3 逻辑体的「逻辑体」= **受控伪代码**；01 验收标准 = Given-When-Then；数据约束 = DDL。
> **「受控」= 只允许下列白名单构造**；超出白名单即视为「自由发挥」——第三环无法翻译，`self-check` 6c / 6d 也无法校验。

### 白名单构造（只允许这些）

| 构造 | 写法 | 说明 |
|------|------|------|
| 赋值 | `x = <表达式>` | — |
| 条件 | `IF <条件> THEN <步骤> ELSE <步骤>` | 条件须为**可判定**的业务表达式 |
| 多分支 | `SWITCH <取值> CASE <值>: … DEFAULT: …` | — |
| 循环 | `FOR EACH <元素> IN <集合> DO …` | **只允许遍历**，不允许自由 `WHILE` |
| 调用 | `<LU-x>(<入参>)` 或 `<实体>.<业务方法>(<入参>)` | 调用本文件其他逻辑单元**必须用其 ID** |
| 状态迁移 | `<实体>.<状态字段>: <旧态> -> <新态>` | 状态名须来自 04 状态枚举 |
| 抛异常 | `RAISE <错误码>(<业务语义>)` | 错误码须 ∈ `接口契约.md` §4 |
| 返回 | `RETURN <结果>` | — |
| 原子要求 | `ATOMIC { <步骤…> }` | 只表达「必须原子」的**业务要求**，不写隔离级别 / 锁 |

### 强制要素（每条逻辑体必须齐备）

1. **入参 / 出参**——取自详述的「输入 / 输出」，不另起名
2. **前置条件**——不满足时的行为须可推出（`RAISE` 或跳过）
3. **错误分支**——每处 `RAISE` 对应一个**已登记**错误码（无凭空错误码）

### 禁止项

- 禁止框架 / ORM / SQL / 缓存 / 锁 / 隔离级别的具体写法（属**工程基线**）
- 禁止在逻辑体中混入自然语言长段落（不可翻译）
- 禁止引用未定义标识符（调用一律用 `LU-x`；实体字段须存在于 `04`）

## 边界
- **分层精简**：系统级标准引用 `../系统级技术标准.md`、系统级目标引用 `../系统级技术规范.md`、模块文件只补差异；禁止重复列举上级规范内容
- **不设计架构**：技术选型/分层/部署/非功能属**外部技术架构**（工程基线承载），一律引用 `../系统级技术标准.md` §5，不在 03 展开；若发现新的统一约定项，回写 `../系统级技术标准.md` 对应节并追加变更记录。
- **模块归纳属需求翻译**：把 FR-x 聚合为模块（业务域/跨切面）是本阶段核心职责；但**不决定**模块内部分层与技术实现（归研发）。
- **接口契约独立成文 · 契约中立**：接口契约已独立为系统级 `tech/接口契约.md`（**唯一权威源**，前后端与测试共享的边界物）；模块 03 §2 承载**后端业务上下文**（引用 `operationId`，不重复 schema），模块 05 §4 只声明**消费方式**（引用 `operationId`），**禁止任何一方二次定义 schema / 状态码 / 错误码**。
- **复杂逻辑内联（已升级为独立建模）**：复杂逻辑不再内联在功能点，而是抽为 03 §3「逻辑单元」（`LU-x`），§2「接口编排」只写调用序列——**逻辑的唯一权威归属地是 §3**，§2 / §1 / §4 一律引用不重复定义。
- **逻辑体表达法受控**：03 §3 逻辑体一律用「逻辑体语法子集」白名单构造（见本 skill 专节）；**01 验收标准的 Given-When-Then 化属 prototype-agent 侧，不在本 skill 范围**。
- **只写业务语义，不写技术方案（全文档判据）**：读接口必写「查询语义」（筛选维度 / 默认排序 / 分页 / 过滤 / 关联加载）；**不写访问技术方案**（ORM / 分页插件 / 缓存 / 读写分离 / 连接池 / 具体 SQL 实现）。判据（唯一）：**换成别的技术栈，结论会不会变？** 会变 → 外部技术架构（工程基线），本项目不产出；不变（查询语义 / 业务约束 / 并发业务场景）→ 必须写。索引落点在模块 04 §3。
- **05 与 03 边界对称**：03 不写具体框架/ORM；05 不写框架选型 / 路由注册方式 / 请求层封装 / 状态库 / 构建配置（均属工程结构常量，由工程配置文件约束）。05 只写「有哪些页面、什么路由、什么权限、组件怎么组成、需要哪些状态、调哪些接口、何时调、校验什么、异常怎么呈现、落在哪个目录」。
- **01 / 02 各司其职**：01 是逻辑与规则主源（03 与 05 §5 来源），02 是交互与展示主源（05 主要来源）；**05 的页面结构不得凭 01 推测**。
- **模块 ≠ 场景 ≠ 代码模块**：03 模块是技术域聚合；01 场景是业务情境；研发代码模块由 03 模块近 1:1 翻译得出，但最终边界由研发定。
- **模块独立文件**：每个模块一份 03 + 一份 05（04 于阶段 3 生成），不会相互覆盖，便于模块化管理和并行工作。
