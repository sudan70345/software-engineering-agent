# 需求解析 Skill — 技术架构阶段 1

## 🛡️ 执行前自检（必做）

执行本 Skill 前必须确认：
1. ✅ 已读取系统级双文件（系统级技术标准.md + 系统级技术规范.md）
2. ✅ 当前项目名与系统目录明确
3. ✅ 本 Skill 产出文件归属正确（tech/ 子目录）
4. ✅ 已明确输入模式（模式 A：读取 prd/系统要求规范.md + modules 的 01 + 02；模式 B：用户直接提供）
5. ✅ **本 Skill 须产出** `../代码工程结构说明.md`（**阶段 1 推导产出**：§1 槽位表含所有权；推导来源与问询边界见模板头部）；单项推不出 → 登记 `TECH-OPEN-*`，**不臆造代码路径**

**若任一项不确定 → 立即执行「CLAUDE.architect.md §上下文恢复检查点」R1-R4 流程。**

> 📌 **权威源引用**：术语定义见 `CLAUDE.md §术语对照表`；确认话术见 `AGENTS.architect.md §阶段 1`；模块归纳判据见 `skills/tech-architecture/SKILL.md §Step 1`。

## 输入（两种模式）
- **模式 A · 接链路（推荐）**：读取同系统目录的 `../prd/系统要求规范.md` + `../prd/系统交互规范.md`（系统级交互规范）+ 项目级 `../../通用异常处理.md` / `../../通用校验规则.md` + `../prd/modules/*/01-*-需求规格.md`（后端规格来源）+ `../prd/modules/*/02-*-UI交互规格.md`（**前端规格来源**），作为上游需求包。
  > ⚠️ **01 与 02 同等必读，不可互相替代**：01 是逻辑与规则主源（FR-x / 业务规则 / 输入输出 / 校验分工 / 异常），02 是交互与展示主源（页面[N] / 功能组件 / 交互行为 / 页面状态 / 页面流转）。阶段 2 的 05 前端规格只能由 02 派生，禁止凭 01 推测页面结构。
- **模式 B · 独立输入**：用户直接提供一份产品规划 / 功能说明 md（可以是整篇或片段）。

> 判定：若当前系统目录下已存在 `../prd/系统要求规范.md` + `../prd/modules/` → 模式 A；否则 → 模式 B。
> 优先模式 A（链路无缝衔接）；仅当没有需求包时退回模式 B。

## 前置条件
- 已确定 `{项目名}` 与系统目录 `document/{项目名}/{system_dir}/`（与需求分析智能体（prototype-agent）**同系统目录**；技术产物写入本系统下的 `tech/` 子目录）。
- 已读取规则：项目级通用规则（`../../通用异常处理.md` / `../../通用校验规则.md`，见上方「输入」模式 A）与系统级 `../tech/系统级技术标准.md`（系统级技术标准，须遵守并维护；该文件须已由阶段 0（tech-common-rules · 门禁 0）确认建立，spec-analysis 进入前必须已存在且已确认）。

## 输出
- **需求解析摘要**（呈现给用户确认；不直接落盘为编号文档，确认后由后续阶段落盘为 03/04/05）
- **模块初步归纳**（module → FR-x 映射草案 + 归纳判据，供阶段 2 建立 03 §1 模块脊柱）
- **缺口清单**（含糊 / 冲突 / 缺失点，须向用户澄清）
- **`tech/代码工程结构说明.md`**（**阶段 1 推导产出**：槽位表 = 逻辑灌装点位唯一权威源 + 所有权标记）——推导来源与问询边界以该模板头部为准；同时向 `系统级技术规范.md` §15「可运行性元数据」登记构建 / 测试命令 · 测试框架 · 启动顺序 · 端口

## 工作流程

### Step 1：获取并解析上游输入
- 模式 A：读取 系统要求规范.md + 系统交互规范.md + 项目级通用规则 + **逐模块读取 modules/*/01-*-需求规格.md 与 modules/*/02-*-UI交互规格.md**，抽取：

  **① 系统级维度**：业务场景总览(系统要求规范 §2：场景[Sx]→涉及FR-x/模块)、角色与权限(系统要求规范 §3)、非功能诉求 NFR(系统要求规范 §4)、模块清单(系统要求规范 §5)、**端范围(系统要求规范 §6.3：Web / 移动端 / 双端并存——05 §7 平台差异的唯一依据；缺失须登记缺口反问，不得自行假定)**。
  **② 后端维度（来自 01）**：功能要点(FR，含所属场景，01 §2)、业务实体(01 §3)、业务规则(BR，01 §4 结构化：触发/判定逻辑/失败输出/降级边界)、输入(含默认值，01 §5)、输出(成功/失败分态+失败提示语义，01 §6)、校验(01 §7)、处理流程(01 §8)、异常(时机/系统处置/用户体验语义/恢复，01 §9)、未决项(01 §10 OPEN-*)。
  **③ 前端维度（来自 02，供阶段 2 的 05）**：页面[N] 与辅助页面[N-A] 清单(02 §1)、功能组件清单与对应 FR-x(02 §4)、关键交互行为(02 §5)、页面状态变体(02 §6)、页面流转与传参(02 §7)、辅助页面（弹窗）归属(02 §9)、未决项(02 §10 OPEN-UI-*)。**只从 02 取，不从 01 推测**。
- 模式 B：解析用户 md，抽取同样维度；无结构则按 01 的章节结构归并（前端维度若源文档未覆盖，登记为缺口反问）。

### Step 1.5：模块初步归纳（module → FR-x 映射）
> 这是 architect「需求翻译 / 中转站」的核心动作：把扁平 FR-x 按统一业务逻辑聚合为模块，供阶段 2 建立 03 §1 模块脊柱。**模块 ≠ 场景**（场景是业务情境、跨模块；模块是技术域聚合）。
- **归纳判据**（5 条：主对象归属 / 同对象聚合业务域 / 跨切面独立 / 跨对象按核心能力归属 / 宁细勿粗），详见 `skills/tech-architecture/SKILL.md §Step 1`。
- 产出映射草案（每条 FR-x 仅归一个主模块）：
  | 模块 | 类型(业务域/跨切面) | 覆盖能力 | 含 FR-x |
  |------|------|---------|---------|
  | M1 用户模块 | 业务域 | 用户 CRUD + 资料 | FR-1、FR-3 |
  | M2 鉴权模块 | 跨切面 | 登录态/权限 | FR-5 |
- 此为**初步分解**（偏细、待阶段 2 细化与用户确认），非最终架构；架构受限下不追求一次到位。

### Step 2：技术视角映射与缺口/冲突分析
从"能否直接落到技术设计"的视角检查：
- **缺口**：需求包未覆盖的技术必要信息（如：预估数据量/并发、是否有审批流、第三方依赖、报表/导出诉求、审计要求）。
- **冲突**：01 §4 业务规则 与 02 §6 页面状态变体不一致；或业务规则与技术可行性冲突（如强一致 vs 高并发）。
- **歧义**：含糊描述（"支持大数据量"→ 具体量级？）。
- **上游未决项**：需求分析智能体（prototype-agent） OPEN-* 是否会影响技术设计（必须登记为技术设计前置依赖）。

产出「缺口清单」：
| 编号 | 类型 | 描述 | 影响 | 需澄清问题 |
|------|------|------|------|-----------|
| GAP-1 | 缺口 | 未给并发预估 | 影响容量设计 | 峰值 QPS？ |

### Step 3：确认门禁 1
向用户展示「技术需求理解摘要」（业务场景/模块草案/缺口清单），确认模板详见 `AGENTS.architect.md §阶段 1 确认门禁`。
- 用户确认 → 进入阶段 2（tech-architecture）
- 含糊项未闭合前禁止进入下一阶段（硬编风险）

### Step 4：记录解析结论
确认后，将解析结论写入 `tech/tech-系统操作记录.md`（首次创建则复制 `templates/architect-agent/system-level/tech-系统操作记录.md` 表头后追加），条目四字段，标记阶段 1。
