## 输入

## 前置条件

- 已完成 CLAUDE.md「调用与决策」Step 0–2：**工程研判**（Step 0 已读取候选工程的 `产品工程摘要.md` 作研判依据；**跨任务一致性研判时需另读 `产品通用规则.md`** 比对标准/术语）、**工程项目归属与任务类型判定**（新建 / 维护现有任务）、**跨任务一致性研判**（定义偏差 / 描述偏差 / 场景重复 / 前后不一致已提醒用户选择「放弃」或「更新」）。

## 调用上下文（只读，不在此决策）

- 若为已有工程下的任务：先读取 `document/{工程名}/产品通用规则.md`，在阶段 1 沟通中复用其角色 / 权限 / 通用标准，并在产出时引用而非重复定义。
- 若为新建工程的第一个任务：在产出后，将其中跨任务通用的角色 / 权限 / 全局业务规则 / UI 标准抽取进 `document/{工程名}/产品通用规则.md` 完成初始化。

> ⚠️ **本 Skill 不做原型生成决策**：是否生成原型（当前绑定 Pencil 方案）由**需求包确认后的决策门禁**统一裁决（定义见 `CLAUDE.md`「调用与决策」）。阶段 1 只负责创建并确认两份文档的业务基线，不得在此询问用户是否做原型。
> ⚠️ **职责边界**：产品功能与业务行为描述规范详见 `CLAUDE.md §职责边界`（唯一权威源），本 Skill 执行时须遵守，禁止在 01/02 文档中写入技术实现定义。
> ⚠️ **工程公共规则**：同工程任务共享 `产品通用规则.md`；通用内容抽取进该文件、任务文档只保留引用，确保单一权威源。
> ⚠️ **两份文档同源一次采集**：阶段 1 同时打通「01 功能侧」与「02 页面侧」的骨架；阶段 2 逐页沟通时**双向落档**（同一轮对话同时写 01 的功能条目与 02 的页面规格），杜绝两遍采集与漂移。

## 工作流程

### Step 1：引导用户提供信息

使用 AGENTS.md 中的引导模板，逐步了解：
1. **端**：移动端 / Web 端 / 多端（若不同端布局差异大，在阶段 2 逐页标注）
2. **功能类型**：自由描述为主，常见示例——表单处理 / 数据分析 / 内容展示 / 后台管理(CRUD) / 交易 / 电商 / 社交 / 工具类 / 混合
3. **需求背景**：业务场景、解决什么问题
3.5. **业务场景（一级容器，必采）**：梳理有哪些**业务场景**——用户在什么情境下要完成什么（如「新用户首单」「日常记录」「账户安全」）。每个场景是一段横切叙事，通常跨多个功能、跨多个页面。**本步建立「场景[Sx]」清单**，作为 01 §2.4 的一级容器；阶段 2 逐页沟通时回填每个场景涉及的 FR-x 与页面[N]，并为每条功能标注「所属场景」。⚠️ 场景是业务情境，**不是技术模块**（模块由下游 architect 归纳）、**不是页面**（页面是 02 的载体）。
4. **目标用户**：用户画像、使用频率
5. **角色与权限**：有哪些角色？不同角色能使用的功能有何差异？（产品级）
6. **范围与非目标**：本期明确要做哪些功能？明确**不做**哪些？（Scope / Non-goals）
7. **关键页面**：每个页面的核心职责（解决什么问题、提供什么服务）——**本步建立「页面[N]」清单，作为 01/02 的共同锚点**
8. **页面关系**：核心页面 / 辅助页面的层级与主·辅关系（用于 02 §3 页面总览）
9. **成功标准 / 验收口径**：怎样算做成？关键验收条件或指标？
10. **UI 风格**：有无参考、风格偏好、品牌规范
11. **非功能需求（NFR）**：性能/并发、安全、合规、可用性、兼容性、可观测性等约束（architect 刚需，阶段 1 必采）

> 📌 **已有工程复用**：若本次任务属于已有工程，第 5 项（角色与权限）、第 10 项（UI 风格 / 品牌）及全局业务规则应优先复用 `产品通用规则.md` 的通用定义，仅补全本任务特有部分，避免重复定义。

> 📌 **术语澄清（必做）**：阶段 1 沟通中识别**易混淆 / 易产生理解偏差**的业务术语（金额类如总金额 / 优惠后金额、时效类如有效期 / T+N、统计类如平均 / 汇总、业务内易混淆专有名词），须与用户确认明确含义与计算规则，写入所属工程 `产品通用规则.md` 的「通用术语表」（§4），禁止在未定义状态下继续推导。

### Step 2：整理信息 → 创建两份文档骨架

阶段 1 **同时创建** `01-需求规格说明书.md` 与 `02-UI交互规格说明书.md`：

> 📌 **模板为单一权威源**：两份文档的完整骨架以 `templates/01-需求规格说明书.md` 与 `templates/02-UI交互规格说明书.md` 为单一权威源。**首次创建时从模板复制**到 `document/{工程名}/{task_dir}/prd/` 并填充占位符（`{工程名}` / `{task_dir}` / `{任务名称}`），不在此内联维护文档结构，避免与模板漂移。

- **01 阶段 1 填充**：§1 文档信息、§2 需求背景与功能概述（含 **§2.4 业务场景总览**——预填 场景[Sx] + 场景描述，一级容器）、§3 角色权限、§4 范围与非目标、§5 约束条件（含 NFR）；§8 业务实体（领域概念）可在阶段 1 预填雏形（从业务架构讨论中识别的核心业务实体）；§9 全局业务规则（如「下架后不可下单」等跨页面规则）也可在阶段 1 预填。§6–§14 在模板中以占位行保留，由阶段 2 逐页追加，并回填每条功能的「所属场景」与 §2.4 场景的「涉及 FR-x / 页面[N]」（复杂功能的 §9 须结构化、§13 须强制穷举，详见模板与 page-specs Skill）。
- **02 阶段 1 填充**：§1 文档信息、§2 设计约束与风格、§3 页面总览（含主·辅页面关系图与页面清单——**区分主页面「页面[N]」与辅助页面「页面[N-A]」**，辅助页面记「所属主页面」；页面记「所属场景」）。§4 逐页规格在阶段 2 逐页填充；§5 全局交互约定、§6 未决项在阶段 2 收尾补充。
  - ⚠️ **术语**：02 的页面内 UI 单元统一称「**功能组件**」（非「功能模块」），每个组件对应一个 FR-x；「模块」一词专属下游 03（业务域聚合），勿在 02 使用。

> 📌 **工程公共规则抽取时机**（必做）：
> - **触发条件**：同一规则/术语/标准在≥2 个页面或功能中出现，或用户明确标注为「通用」
> - **抽取内容**：角色与权限定义、通用业务规则、品牌/UI 标准、术语表（**不含工程基本信息**，工程是什么见 `产品工程摘要.md` §0）
> - **抽取动作**：将通用内容写入 `document/{工程名}/产品通用规则.md`，任务文档内改为引用（如「角色定义见 产品通用规则.md」）
> - **维护时机**：新建工程时用于初始化；已有工程时增量补充/修订，并在 §10 维护记录追加一行
> 
> > 📌 详细抽取判据与流程详见 `CLAUDE.md §工程公共规则`，本 Skill 仅执行不决策。

### Step 3：展示给用户确认（确认门禁 1）

将两份文档的业务基线摘要展示给用户（参见 AGENTS.md 确认门禁 1）。

- 用户提出修改 → 更新文档（两份同步），重新确认
- 用户确认 → 推进到阶段 2（逐页面双向落档）
