# 业务架构沟通 Skill — 阶段 1

## 输入

- 用户提供的需求描述（来自阶段 1 对话）

## 前置条件

- 已完成「工程项目归属判定」（见 CLAUDE.md）：确定 `{工程名}` 与任务目录 `prototype/{工程名}/{task_dir}/`，并已创建目录（新建工程时同时创建 `project-common-rules.md`；`工程摘要.md` 由 delivery 首次刷新时从 `templates/工程摘要.md` 懒创建）。

## 调用上下文（只读，不在此决策）

- 若为已有工程下的任务：先读取 `prototype/{工程名}/project-common-rules.md`，在阶段 1 沟通中复用其角色 / 权限 / 通用标准，并在产出 01 时引用而非重复定义。
- 若为新建工程的第一个任务：在产出 01 后，将其中跨任务通用的角色 / 权限 / 全局业务规则 / UI 标准抽取进 `prototype/{工程名}/project-common-rules.md` 完成初始化。

> ⚠️ **本 Skill 不做原型生成决策**：是否生成原型（当前绑定 Pencil 方案）由**需求包确认后的决策门禁**统一裁决（定义见 `CLAUDE.md`「调用与决策」）。阶段 1 只负责产出并确认 `01-business-architecture.md`，不得在此询问用户是否做原型。
> ⚠️ **职责边界**：本文件描述**产品功能与业务行为**，不设计技术方案（数据模型、API、技术栈、字段级实现契约归下游技术架构 agent）。
> ⚠️ **工程公共规则**：同工程任务共享 `project-common-rules.md`；通用内容抽取进该文件、任务文档只保留引用，确保单一权威源。

## 输出

- `prototype/{工程名}/{task_dir}/01-business-architecture.md`

## 工作流程

### Step 1：引导用户提供信息

使用 AGENTS.md 中的引导模板，逐步了解：
1. **端**：移动端 / Web 端 / 多端（若不同端布局差异大，在阶段 2 逐页标注）
2. **功能类型**：自由描述为主，常见示例——表单处理 / 数据分析 / 内容展示 / 后台管理(CRUD) / 交易 / 电商 / 社交 / 工具类 / 混合
3. **需求背景**：业务场景、解决什么问题
4. **目标用户**：用户画像、使用频率
5. **角色与权限**：有哪些角色？不同角色能使用的功能有何差异？（产品级）
6. **范围与非目标**：本期明确要做哪些功能？明确**不做**哪些？（Scope / Non-goals）
7. **关键页面**：每个页面的核心职责（解决什么问题、提供什么服务）
8. **页面流转**：从 A 到 B 的流程路径（宏观主路径）
9. **成功标准 / 验收口径**：怎样算做成？关键验收条件或指标？
10. **UI 风格**：有无参考、风格偏好、品牌规范

> 📌 **已有工程复用**：若本次任务属于已有工程，第 5 项（角色与权限）、第 10 项（UI 风格 / 品牌）及全局业务规则应优先复用 `project-common-rules.md` 的通用定义，仅补全本任务特有部分，避免重复定义。

### Step 2：整理信息 → 输出业务架构文档

写入 `prototype/{工程名}/{task_dir}/01-business-architecture.md`，结构如下：

> 📌 **工程公共规则抽取（必做）**：01 定稿后，将其中**跨任务通用**的内容抽取进 `prototype/{工程名}/project-common-rules.md`：
> - 角色与权限定义、通用业务规则、品牌 / UI 标准、术语表。
> - 抽取后，01 内对应处改为**引用**（如「角色定义见 project-common-rules.md」），不重复全文。
> - 新建工程时此步用于**初始化**该文件；已有工程时用于**增量补充 / 修订**并保持单一权威源。

```markdown
# {任务名称} — 业务架构描述

## 1. 需求描述
- **端**: [移动端 / Web端 / 多端]
- **功能类型**: [自由描述，可参考：表单处理 / 数据分析 / 内容展示 / 后台管理(CRUD) / 交易 / 电商 / 社交 / 工具类 / 混合]
- **背景**: [业务背景]
- **目标用户**: [用户画像]
- **用户场景**: [使用场景、使用频率]

## 2. 范围与非目标
- **本期范围（In-scope）**: [明确要做的功能清单 / 目标]
- **非目标（Non-goals）**: [明确本期不做的内容，避免下游范围蔓延]

## 3. 角色与权限（产品级）
> 通用角色与权限定义见 `project-common-rules.md`；下表仅列本任务涉及 / 特有的部分（已有工程可大幅简化、引用即可）。
| 角色 | 描述 | 可使用的主要功能 |
|------|------|----------------|
| [角色A] | [是谁] | [功能1、功能2…] |
| [角色B] | […] | […] |

## 4. 验收口径 / 成功标准
- [怎样算做成？关键验收条件或指标，例如：用户能在 3 步内完成下单；管理员可独立维护类目]

## 5. 页面拆解
### 页面[N]: [名称]
- **核心职责**: [解决什么问题、提供什么服务]
- **定位**: [核心页面 / 辅助页面]
- **功能边界**: [包含什么功能、排除什么功能]
- **异常状态**: [如有，描述异常状态处理]

### 页面[N]: [名称]
- **核心职责**: […]
- **定位**: [核心页面 / 辅助页面]
- **功能边界**: [包含什么功能、排除什么功能]
- **异常状态**: [如有，描述异常状态处理]

...（共 N 页，编号统一为「页面[N]」）

## 6. 全局业务规则（产品行为，非技术实现）
- [跨页的产品规则/约束，例如：类目下存在商品时禁止删除该类目；商品下架后不可被下单]
- [状态流转的产品行为，例如：商品可 上架↔下架，下架态不对外可见]

## 7. 页面流转（宏观主路径）
> 本表描述跨页的宏观流转；逐页的微观交互（点击、弹窗、反馈）在 `02-page-specs.md` 的「交互定义」中描述，二者应一致，以 02 为权威细节。
| 来源页面 | 触发操作 | 目标页面 | 说明 |
|---------|---------|---------|------|
| 首页 | 点击商品 | 详情页 | 跳转 |
| ... | ... | ... | ... |

## 8. UI 约束描述
- **风格**: [风格描述]
- **参考**: [参考产品/链接]
- **品牌规范**: [如有]
- **色彩倾向**: [如有]
```

### Step 3：展示给用户确认

将文档摘要展示给用户（参见 AGENTS.md 确认门禁 1）。

- 用户提出修改 → 更新文档，重新确认
- 用户确认 → 推进到阶段 2
