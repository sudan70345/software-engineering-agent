# 项目长期约定（software-engineering-agent）

## 1. 工程链路与双智能体
三阶段链路：`需求分析(prototype-agent) → 技术分析(architect-agent) → 编程智能体(外部)`。
- prototype-agent 产出需求包（01-需求规格说明书.md + 02-UI交互规格说明书.md）= 上游产品功能基础说明。
- architect-agent 产出 tech/（03-技术规格说明书.md + 04-数据模型说明书.md），定位=**需求翻译器/中转站，不做架构设计**（分层/技术选型/部署归工程级 `技术通用规则.md`）。
- 两智能体同工程共享 `document/{工程名}/` 与 `skills/`，同任务共享 `{任务名}_{YYYYMMDD}/` 锚点；prd/ 与 tech/ 子目录数据独立，architect 只读 prd/、只写 tech/。
- 独立指令文件：prototype=CLAUDE.md/AGENTS.md；architect=CLAUDE.architect.md/AGENTS.architect.md；均在 opencode.json 注册。

## 2. 四层统一模型（2026-07-11，当前权威结构）
同一原子功能（**FR-x 为唯一脊柱键**，贯穿四层）在四种容器视角：
- 01 需求：**场景**（业务情境，一级容器 §2.4）→ 用户故事(FR-x)
- 02 UI：**页面[N]/辅助页面[N-A]** → 功能组件(FR-x)
- 03 技术：**模块**（技术域业务聚合）→ 功能点(FR-x)
- 研发：代码模块 → 代码功能

术语三件套互不同义：02「功能组件」(UI单元) ≠ 03「模块」(业务域容器) ≠ 研发「代码模块」。
场景与模块**多对多**（经 FR-x），模块跨场景抽取。
- 01 引入场景但**不改 §6–§14 编号**（经 §2.4 子节 + §6/§7「所属场景」列落地，避免全仓重编号断裂）。
- 02 弹窗二分：复杂弹窗（创建/修改/配置类，独立表单+校验+提交）→独立辅助页面[N-A]（挂主页面、记所属场景）；简单弹窗（提醒/反馈/确认）→主页面内联一句话。

## 3. 03/04 architect 结构（2026-07-11）
- 03 = **模块→功能点两层**：§1 模块划分总览（模块归纳判据 + 模块总览表 模块/类型/覆盖能力/含FR-x/待校准）；§2 逐模块（模块定义/边界段：核心业务对象/统一业务逻辑/聚合FR-x/关联场景/关联模块/边界 + 功能点块）；§3 错误码；§4 技术风险。
- **模块归纳判据(5条)**：①主对象归属 ②同对象聚合为业务域模块(覆盖完整CRUD) ③跨切面能力独立成模块(鉴权/通知/日志，被多模块共享且独立演进，**不并入业务模块**) ④跨对象功能按核心能力归属、调他模块记「关联模块」 ⑤粒度宁细勿粗。模块归纳属需求翻译非架构设计；architect 拿不到完整工程结构，产物为**初步分解(偏细·待人工校准)**，人工校准不在本项目职责内。
- **功能点 9 子项**：①功能描述 ②输入 ③校验 ④处理逻辑(含复杂逻辑/状态机/算法) ⑤输出 ⑥异常(功能点级业务策略) ⑦接口契约(机器可读:端点·方法·schema·错误码·OpenAPI) ⑧接口初步规划(伪代码，不写框架/ORM) ⑨关联数据→04。机器可读(⑦)与伪代码(⑧)并存。
- 04：实体按 03 §1 模块分组，「所属模块」继承 03 归纳结果(M1/M2…)；从 03 §2 功能点输入/输出/关联数据派生。六维确认(表/字段/建表DDL/索引DDL/关联/状态机)。
- 阶段 0+3 阶段 + 4 门禁：0=技术通用规则确认 / 1=需求解析(含模块初步归纳草案) / 2=技术规格(模块脊柱+功能点9子项) / 3=业务表结构。
- 历史：05-接口设计、06-模块详细设计模板已删（并入03）；skills/api-design、skills/module-design 已删。

## 4. 双段式工作流（prototype）
- 第一部分·需求分析(必做)：阶段1 业务架构(同时创建 01+02 基线，含 §2.4 场景 + 主/辅页面总览) → 阶段2 逐页双向落档(同轮向 02 §4 写页面规格[功能组件/主辅类型/所属场景]、向 01 §6/§7 追加功能条目[标所属场景]+§9-§13)。两份经「页面[N]」对齐。
- 决策门禁(需求包定稿后三选一)：①原型设计(Pencil) ②技术分析智能体 ③结束。
- 第二部分·原型生成(可选)：调 Pencil MCP 前提示用户开 Pencil 桌面应用+启动 MCP。

## 5. 01/02 内容约束
- 需求包**工具无关**：禁写 Pencil/绘图实现细节；页面用中性「页面[N]」，Pencil 命名 P{N}_/P{N}D{M}_ 由 pencil-executor 推导不回写。
- 需求包**严禁技术实现内容**(接口/数据模型/技术选型)，归 architect；访谈中用户提及记为「用户技术倾向/约束」交接时移交。
- 01 §8 业务实体=业务概念目录(领域词汇)，仅列概念与业务属性，禁写字段类型/表名/索引。
- 01 五大模块结构化：§6 用户故事(验收多条·覆盖成功/失败/边界态)、§9 业务规则(触发/判定/失败输出/降级，禁写事务回滚/幂等键/锁)、§10 输入(增默认值列·嵌套用each_item)、§11 输出(成功/失败分述·失败仅记提示语义)、§13 异常(强制穷举·发生时机/系统处置/用户体验语义/恢复策略)。弹性：复杂展开、简单精简。
- 失败提示边界：语义/映射规则归 01(供 architect 做错误码映射)，视觉呈现(Toast/弹窗/位置)归 02。
- 通用术语澄清：金额/时效/统计/易混淆专有名词须与用户确认含义与计算规则，写入工程 `产品通用规则.md` §4 通用术语表。
- 未决项分置：01 §14(OPEN-x 功能侧)、02 §6(OPEN-UI-x)；与任务结果摘要闭环。FR-x/BR-x 编号。

## 6. 三层记录体系
「当前态/历史」分离，互不污染，产品侧(prd-)与技术侧(tech-)各独立：
- 工程级 `产品工程摘要.md`(原地更新)：§0 工程概览(工程名/业务领域/一句话定位=工程基本信息只在此) / §1 任务清单(目录·状态·结论·链接) / §2 工程维护记录。
- 任务级 `prd-任务结果摘要.md`(独立·原地更新)：状态封面，指向 01/02 与原型。
- 任务级 `prd-任务操作记录.md`(单文件·只追加)：四字段 计划时间/执行内容/执行结果/复核结果。
- 刷新时机：01/02 或原型变动→刷结果摘要+工程摘要；每次操作后→追加操作记录。
- 小版本号规则：每次 01/02 更新/优化，`文档版本`小版本+1(v1.0→v1.1，结构性重构才大版本+1)；architect 因上游更新而更新时 tech 文档(03/04)小版本同步+1。

## 7. 进入执行流程(CLAUDE.md「调用与决策」Step 0–5 为唯一权威)
- Step 0 工程研判(必做)：读候选工程 `产品工程摘要.md` 作研判依据(`产品通用规则.md` 阶段1读)。
- Step 1 归属+任务类型判定(新建/维护，维护读原 01/02 作基线)。
- Step 2 跨任务一致性研判(必做)：识别 定义偏差/描述偏差/场景重复/前后不一致，发现即提醒用户选「放弃」或「更新」。
- Step 3 执行；Step 4 决策门禁三选一+小版本号；Step 5 技术侧联动(维护且 tech/ 已存在→提醒调 architect 对齐，其 tech 小版本同步+1)。

## 8. 工程级两份文件职责严格分离
- `产品工程摘要.md`=工程全貌(§0 概览[工程基本信息只此]/§1 任务清单/§2 维护记录)。
- `产品通用规则.md`=纯标准(§1 角色权限/§2 通用业务规则/§3 通用UI标准/§4 通用术语表/§5 通用模块清单/§6 规则文件变更记录)，**禁写工程基本信息**。
- 架构侧镜像：`技术工程摘要.md`(§0 概览+技术栈/部署 /§1 技术任务清单 /§2 维护记录)；`技术通用规则.md`(§1 并发容量/§2 语言/§3 框架/§4 规范/§5 约定/§6 领域模型/§7 分层/§8 部署/§9 非功能/§10 变更记录)。
- business-architecture 抽取通用内容只抽标准类，工程基本信息不入通用规则。

## 9. 命名与单一权威源
- 模板/生成文件统一中文，同名文件加 `prd-`/`tech-` 前缀(`交接索引.md` 不改名)。
- 技术模板带序号+说明书：仅保留 `03-技术规格说明书.md`、`04-数据模型说明书.md`(模板名=生成文件名)。
- skill 不含模板：模板内容只放 `templates/`，skill 仅引用(首建从模板复制填占位符)，避免漂移。
- `templates/01-需求规格说明书.md`、`templates/02-UI交互规格说明书.md`、`templates/03-*`、`templates/04-*` 为骨架唯一权威源。
- 决策门禁/工程归属判定逻辑唯一在 CLAUDE.md；原型端 Critical 约束权威源=`skills/pencil-executor/SKILL.md`；其余文件仅引用不另立。
- `skills/<dir>/` 目录名(如 tech-architecture)为加载标识不动。

## 10. 工作约定
- **流程类/重定义改动须先给方案对齐、经确认再落地**，不得跳过确认直接改文件；方案须覆盖权威落点文件+步骤+超出用户原话的自行解释(显式标注)。可用 AskUserQuestion 逐项确认补充解释点。
- `document/` 下历史产物(旧格式任务目录)属用户自有内容，维持现状不动、不迁移、不纳入整改对象。
